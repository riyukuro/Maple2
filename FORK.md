# Maple2 for the KMS 2525 client

This fork is upstream [Maple2](https://github.com/MS2Community/Maple2) with fixes for the Korean MapleStory 2 client, build 2525. The branch is `kms2525`. Upstream's README.md is unchanged, which keeps merges from upstream simple. Setup and running are the same as upstream.

## How packet layouts are checked

Packet layouts are checked against the client source, not against another server. For each packet type and sub-type, a checker compares two things:

- Client to server: does the server read exactly the bytes the client's writer sends?
- Server to client: does the server write exactly the bytes the client's reader expects?

Each row gets one verdict:

- **pass:** the bytes match exactly.
- **warning:** the server writes more bytes than the client reads (trailing bytes).
- **fail:** the server reads past the end of what the client sends, the client would misread what the server sends, or the server does not handle a sub-type the client sends.
- **not checkable:** the client's reader or writer could not be followed automatically, or the server's code needs game state before it reads.

Every fix in this fork names the client function it follows (a file and line under the client source). The commit message quotes the checker's line before and after.

Results today:

| direction | rows | pass | warning | fail | not checkable |
|---|---|---|---|---|---|
| client to server | 680 | 239 | 5 | 67 | 369 |
| server to client | 1,193 | 592 | 4 | 0 | 597 |

The 67 client-to-server fails are all sub-types the server does not handle (listed below).

Server-to-client rows whose layout depends on client state are checked once per branch the client can take; a row passes when one branch reads the packet exactly. Of the server-to-client passes, 10 are weak (only a branch that ignores the packet, or a guessed condition, fits).

The four server-to-client warnings are kept on purpose; in each the client reads a prefix and ignores the rest:
- Trade sub-type 13 carries a trailing byte that the official server sends too.
- The skill state packet (sub-type 6) carries an extra int that shifts fields the client reads and then discards.
- The achievement favorite packet has no reader in the client (it handles sub-types 0 to 2 only).
- The skill macro load (sub-type 0) is read by a client handler that acts on sub-type 2 only.

## Fixes so far, by system

- **Opcodes:** client-to-server opcodes 0xAB to 0xBC are renumbered to the client's list.
- **Emote:** the list entry is 26 bytes; the favorite request (sub-type 4) is read as the client writes it.
- **Trigger:** the sub-type numbers are the client's (skip cutscene, UI, load script, save script, discard script).
- **Trigger dungeon variables:** a variable never set reads 0; no client code or table gives a start value.
- **Trigger score board:** score_board_score compares only in a field whose script called score_board_set_score; elsewhere it is the old test (the threshold compared with 0, so GreaterEqual passes). No kill, pickup or packet score reaches the board (the client only shows it), so 02020063/02020065 battle_1 (800 points) and 99999840/99999841 would otherwise never end.
- **Trigger dungeon room timer:** a dungeon room whose row has a timerType (clock or gauge) and a durationTick gets that room timer when its first player enters; players who enter later get the running timer and its lap marks. With isExpireTimeOut the room closes when the time runs out, as bonus maps do. Without it, the time running out only makes dungeon_timeout pass. The actions follow the shipped scripts' own comments on them. dungeon_set_end_time ends the time function, so dungeon_timeout no longer passes; the room still closes at its time with isExpireTimeOut, which the scripts note must be blank for set_end_time to work. dungeon_close_timer closes the timer window (client command 5). dungeon_stop_timer stops the time and closes the window (4). dungeon_reset_time runs the timer again for the given seconds (2). dungeon_set_lap_time and dungeon_move_lap_time_to_now set a gauge mark, in milliseconds from the start, and send all marks (3). Without a room timer they do nothing and dungeon_timeout stays false. Choice: the server starts the timer at the first player's entry; the client does not show when the official server started it.
- **Dungeon missions:** a dungeon room's missions (its partyMissions, then its userMissions, the client's order) are now sent when a player enters a room field. The server first sends RoomStageDungeon mode 0, which is where the client makes its mission list and registers the DungeonMission handler. Missions score by the client's DungeonMissionData::GetScore. maxScore is split into applyCount steps; a row without applyCount has one step. A penalty mission starts full and loses a step's score per count. DamageToNpc counts a player's damage to the npc named in value2 (any npc without it): one step per value1 / applyCount. LastHitNpc counts a step when the player's hit kills an npc in value1. dungeon_mission_complete fills a mission as before. A user mission counts for the acting player. Choice: a party mission counts in every player's record of the room, because the client keeps one list per player. DeathCount counts a step at each death of the player in the room (all 46 rows are penalty, named for not dying). DamageBySkill counts a step at each hit (not a miss) on the player by a skill in value1; a row with value2 needs that skill level (one row). GainBuff counts a step when a buff in value1 is put on the player; a refresh of a buff it already has does not count (choice). PlayTime gets its full score when the room is cleared within value2 seconds of the dungeon start: every row's name gives a minute limit that is value2 / 60, value1 is not read, and the start is the room's entry (choice: the names do not say whether the time starts at the boss). The PlayTime packet's two times stay 0, the client shows nothing from them. dungeon_first_user_mission_score compares the sum of the first entrant's user mission scores. In the fame challenge rooms (one player each) that is the score the client's reward window shows.
- **Trigger dungeon level:** dungeon_level compares the room's groupType (2 raid, 3 chaos raid; the scripts' states are named so), not its dungeonLevel, which is a character level. Outside a raid or chaos raid room it keeps the old answer (3), so a script that tests only 2 and 3 still goes on.
- **Trigger dungeon max user count:** dungeon_max_user_count compares the client's DungeonRoom::GetMaxUserCount for the party size the room was made with (with isChangeMaxUser the size held between 2 and maxUserCount, else maxUserCount). The scripts test 1 to 4 only, so outside a dungeon room and in a 6 or 10 user room it keeps the old answer (1); dungeon_common/checkusercount has no other way on in a room.
- **Colosseum continue-play:** after the intro the Colosseum scripts run talk_npc on Nagi's spawn point; the server now starts that npc's talk with each player, as a click does (the client opens the talk window for a Respond it did not ask for, `UITalkManager::OnTalkPacket`). The choice's script function sets the DungeonPlayType user value (1 new game, 2 continue). The npc's script conditions `receivedRewardDungeonID` (a reward of the room was taken in its period, so the continue is offered) and `completeRewardDungeonID` (all were, so continue starts a new game) are read from the server pack's npcScriptCondition rows, which the parser does not read; their meaning is the server's reading of the names and the script flow (the client has no such table). Taken is the client's `DungeonRecord::GetBonusRewardCount` (the record's count while its cooldown period runs) against the room's rewardCount (`DungeonRecordCli::HasCountLeft`). set_user_value_from_dungeon_reward_count sets its key to that count of the room's one player, which for the Colosseum is its rounds cleared, so ClearRound starts the next round. A run that loses a round after the first ends with dungeon_clear uiType None; the server now clears the room there without the clear banner, so its rewards and the rounds it cleared are saved (before, only a run of all 13 rounds saved its rounds). A room takes one result: a later dungeon_clear or dungeon_fail changes nothing (no second result packet, clear count or dungeon_clear condition; logged at debug). The Colosseum is left out of that, because its script goes back to its start after each end and the next run in the same room ends with its own clear or fail. The conditions need a re-ingest; until then their rows check nothing, so continue is offered and always starts a new game.
- **Item merge:**
  - Request and response sub-types are renumbered to the client's.
  - The option preview (Select) is written in the client's layout.
  - The merge table row is found as in the client: by the item's equip subtype for a material of subtype 1, else part 0, with the level limits and the row's `partLimit` list. A slot without `part` is part 0, as the client reads it (the parser gives 1; the ingest stores it under 0, so it needs a re-ingest). The materials offered are every inventory item the table answers for, asked by its table id, not the table's keys looked up as item ids. The list is read at ingest from the client's `table/itemmergeoptionbase.xml` (the played client's pack has the lists; the data folder's has none), so it needs a re-ingest; rows without it are not judged by it.
  - The merge table id is the material's `param1`, as in the client, when the ingest has the played client's pack (`MS2_PLAYED_CLIENT_XML`): the ingest reads it from that pack's `itemdata/*.xml`, and a material with a table id is asked by it first. Without that pack the table is asked by the material's item id. The hand copies of table 37000055 for 37000056..63 are made in both cases, only for an id with no rows of its own, so they serve only a material that got no `param1`. The data parser's item `Property` class has no `param1` field; with one, the data folder's own item xml could give it (the present data folder's item xml has no `param1` at all).
  - Known limit: the server's item rows come from the data folder's item xml, which is of another version than the played client's. There the merge materials have subtype 21 and 22 (the client's 1 and 2) and equips have subtype 0 or 16 (the client's is the id's kind, 12 to 83). So the equip subtype is taken from the item id (`id / 100000 - 100` for 112xxxxx to 183xxxxx, which holds for every equip in the played client's item data), and a material that is not of subtype 1 is still asked by part when its table has no part 0 row.
- **Ride:**
  - RideSync reads one trailing int per record.
  - The ride start request carries a byte after the object id, and the response echoes it.
- **Mentor:** the server no longer sends an initial packet that the client has no reader for, and its writer is removed.
- **Party:** cancel party search reads one byte; the dungeon match confirm (sub-type 31) has no body; the survival squad register is sub-type 55.
- **Party dungeon match (32, 33, 34):** a matchmaker in the World server. The rules are the user's choice (11-11), not read from the client:
  1. A match fills up to the room's maximum user count, dungeonroom.xml maxUserCount (the dungeon or raid cap), also for an isChangeMaxUser room. The client's DungeonRoom::GetMaxUserCount is not used for the match: for such a room it is the party size held between 2 and maxUserCount, the size of a room already made, so a search would count as full at 2.
  2. The party leader can stop the search early and go with the members found so far, at least the room's minimum. The client has no start-now control (no button, sub-type or confirm reply for it), so the closest client path is used: Party 34 (cancel) by the leader. When the search found someone and the party has at least the minimum of one of its rooms, the party enters that room; otherwise the search stops and the party stays as it is.
  3. A searcher joins an existing searching party for that room, the largest one with room for them, before a new party is started.
  4. The smaller goes into the larger, and on equal size the later into the earlier, whenever a group starts, as long as the merged size is at most a shared room's maxUserCount and the larger party's capacity. A party that starts a search merges into the largest searching party of the same kind, at least its size, that shares a room with it (the earliest on a tie); else it starts its own group, and that group then takes in the waiting smaller groups of its kind that share a room with it, the largest first, then the earliest, while they fit (their parties move into it as in a merge). The joining party's members move into the larger party (they leave theirs, which goes without a disband message) and the found count rises by their number. A merge or pull that fills the cap makes the room. A matched party cannot search again (error 43) and is not disbanded on a leave or kick while another member is online until its room is set; a party gone before then has its room destroyed. When a member move fails, the groups are put back as they were and no room is made; a party with a dungeon room set does not search (error 43) and is not merged.
  - From the client: Party 32 with no room ids searches the client's DungeonRoomTable::GetMatchRooms rooms (group types 1 and 2 by gear score, level limit and id, from the lowest member's level and gear score, at most DungeonMatchRecommendPickCount); with ids, only the picked rooms of the match kind whose level limit the lowest member meets. Party 33 searches its one room. The match kind is the client's map of the room's group type (normal and raid 1, worldBossDungeon 2, event 3, lapenta 4). The register reply (0x1e) and Party Load write the searching bits the client tests (bit kind; Load wrote a bool before); a stop writes 0. A match sends every member the match-found box (0x1f, which has only an OK button) and makes the room as a party dungeon, so the members enter it as from the party dungeon window.
  - Chosen here (neither the client nor the user settles it): no confirm wait and no decline, as the box has OK only; a member who does not press OK can still enter through the party dungeon. When several rooms are full, the lowest room id. Between groups of the same size, the one that started first. A joiner narrows the group to the rooms both search. Party 34 from a member who is not the leader gets error 40 (s_dungeonMatch_error_isNotChief); a Party 34 of another kind than the party's search, or with no search, changes nothing. A solo searcher who starts their own group gets a party of one (loaded before the register reply); a joiner or a merging party loads the party it moved into. Every member of the party counts for the group, its space, its full check and the leader's early start, online or not, so a party never passes the room's maxUserCount when someone comes back: a member who logs out keeps a slot, and the leader can kick them or start early. A leader who logs out (or is found offline before a search) hands the party over to an online member and the search goes on with the new leader; it stops only when no member is online. An invite, a leave or a kick resizes a searching group (it is matched when it becomes full, and stops when no room holds it). A searching party is not disbanded on a leave or kick while another member is online, so a party of two keeps its search for the member left; a disband ends the search with the stop (0x1e) first. When the search ends (stopped, cancelled, or its room cannot be made) a party of one is disbanded, with the disband message. When the room cannot be made the stop has already been sent. A search of a kind other than 1 with no picked room has no rooms and gets no reply. A party too large for every picked room gets no reply. The reward flag of Party 32 is not used; the inside-dungeon error (42), the client's enter count limit and the rooms' hidden flag and sortOrder (not ingested) are not checked. The register announce bool of 0x1e stays true. The party and queue state are under one lock in the World server; the channel calls a step makes (broadcasts, the room) are collected and made after the lock is released. A party that moves away or is disbanded has its Party Finder listing removed. A join (an invite accepted, a Party Finder join) is refused with error 19 (the party is full; the client has no error of its own for it) while the party is matched and its room is being made, and while a dungeon room is set and the party holds that room's maxUserCount (also a room the leader made).
- **Room dungeon:** the dungeon result is sub-type 10; the stage packets write the int, byte and bool the client reads (create) and nothing after the sub-type (clear). A room is refused for a party larger than the dungeon's user maximum: a rule of this server, the client's dialog does not test it.
- **Interact object:** the start of an interaction keeps only objects in reach, and the end of an object that is not gathered is taken only in reach. Rules of this server: a gathered object's reach is the client's MasteryObjectInteractionDistance constant; any other object's reach is 1500 (the client tests the object row's own interactionDistance, which the server does not load); every reach test has 150 (one block) of slack for position lag; a reach constant of 0 tests nothing. Farming and breeding cubes are tested the same way with the constant.
- **Beauty:** a new item (sub-type 3) reads the long between the item id and the appearance; the fee of sub-types 3, 5, 21 and 22 is taken only after the change succeeded. Sub-types 17 and 19 extend the saved style slots by BeautyStyleExpandSlotCount1time for BeautyStyleExpandSlotPrice merets, up to BeautyStyleMaxSlotCount extra slots; 17 then saves the hair it names.
- **Party search:** Remove sends sub-type 1, and the error's request type is one byte.
- **Ugc:** the confirmation request reads the client's two strings.
- **Ugc 0 (upload failed):** the client sends one byte when its picture upload failed. What the official server did with it is not proven. This server gives the fee of mode 1 back once, only for the character's own upload that was paid and has not been confirmed; a second mode 0, or one with no such upload, does nothing. A new mode 1 gives the unfinished one's fee back as well, so a retry costs the fee once. A banner's unfinished designs are taken off the slots they were put on, also when the character has left that field; the slots stay reserved. A design coupon comes back as a new item of the same id: the expiry and binding of the used one are not kept, and with a full inventory it is lost (logged). A mode 3 whose kind is not the upload's finishes nothing, so that fee can still be given back.
- **Ugc guild kinds:** the emblem upload reads the client's guild id and needs the emblem right (64), as the client's button does. The client asks for no rank right before a guild house poster upload, so any member may put one up; the poster id must be one of the house's poster objects. A confirmation makes only the upload that the same session started the emblem or poster.
- **Ugc banner slots:** a reserved slot belongs to the character that reserved it (mode 19); an upload from another character is refused whole and costs nothing. The owner is kept in memory only, so it is lost at a restart, when the field is disposed (an empty field, after 10 minutes) and on another channel; a reserved slot without a design then has no owner and takes an upload from anyone at the usual price, and the first character that reserves its hour again (mode 19) holds it. The 24 bound below starts again with it. A slot with a design keeps the design's character. Server rule, not from the client (which sends the hours of one day, 24 at most, and shows no limit): a character holds at most 24 reserved slots without a finished design on a field (a design whose picture never arrived counts), and an hour that is over cannot be reserved.

- **Maps the played client does not have:** the server sends a map by id only (RequestFieldEnter) and the client looks the xblock up in its own field table. A pack built for an older client keeps a row for every map id in `table/fielddata.xml` but empties the rows of the maps that version lacks; sent to such a map the client loads nothing and hangs, and it hangs again at the next login because the character is saved there. Not set, nothing is marked and nothing changes; a pack without that table marks nothing. With the 2020 data pack and the older KR client it was tried with, 13 maps are marked (10 with an empty row, 3 with no row) and 10 portals lead to them, 9 of those from maps that stay open. The mark takes effect with the next ingest.

- **Ability window:** learn (mode 2) and reset (mode 1) are handled; the GM learn-all request (mode 3) is not. - **Skill tree (Job 9 save, Job 11 auto distribute):** both send the whole tree (id, level, learned per skill) after the client's own check (`UISkillBookTreeDialog::RequestJob`, `SkillPointSimulator::Validate`). The server now repeats that check on the tree it would store and takes it whole or not at all: per rank, the points spent (a base skill's levels above 1, any other learned skill's level) are within the points from the level (`JobSystem::GetLevelSkillPoint`: none below 10, the base rank one a level from 10 up to `SkillPointLimitLevel1`, the awakening rank one a level from 60 up to `SkillPointLimitLevel2`) plus the extra points of that rank; each learned skill is within its max level; and its level's `upgrade` element is met: the character level, the listed skills learned at their levels in the sent tree, and the listed quests completed. A refused tree is not stored, and the answer (9 or 11) carries the stored one: the client's Job error mode has only job-advance texts, and it re-reads the whole tree from 9 and 11. Before, both took any level up to a skill's max. Not settled from the client, the server's own reading: the client marks a quest as needed when it is rewarded, the server takes a completed quest (the data lists several quest ids per level, the client's code one); the `money` of an upgrade element is not charged, as the client's check has none; skills the client gets outside the tree (its extra flag) have no server counterpart; the bonus value after the extra points is sent as 0, so it adds nothing. The upgrade elements are a new part of the skill metadata and need a re-ingest; until then no requirement is checked, only the points and the max level. Constants ingested before the two limits were added read as 0, and then the points are not checked either.

- **NPC AI summon:** an AI summon node spawns npcs. Its npcId is a 1-based index into the summoner's aiInfo `summonNpcIDs`: the nodes use 1 to 48 and never 0, and in the 473 npc rows whose AI file was found the highest npcId is never past the list. The list is read from the npc xml at ingest (the file parser does not read it), so the npc table needs a re-ingest; rows ingested before summon nothing. A run spawns `npcCount`, while at most `npcCountMax` of the summoner's summons of the node's `group` are alive. A summon stands at `summonPos` (a map position) or at the summoner plus `summonPosOffset` (no node gives both), scattered on the ground within `summonRadius` X and Y, and snapped to the navmesh. It faces `summonRot`; one next to the summoner without a rotation faces as the summoner does. `delayTick` (milliseconds) delays the spawn, and `lifeTime` (under 1000 seconds, from 1000 milliseconds; see AI summon lifeTime below) removes the summon. A summon of a node with `master="None"` stays when the summoner dies or leaves; every other summon is removed with it. ## Database migrations
The servers do not migrate the game database when they start. After an update that adds a migration (`Maple2.Server.World/Migrations`), run `dotnet ef database update` in `Maple2.Server.World` (the ingest runs the same command) before the servers start. Without the `home-block` table of `AddHomeBlockTable` every login fails, because the home block list is read at login. Without the `nurturing-daily` table of `AddNurturingDaily` feeding a housing pet or playing with one fails (the daily record of feedings and plays is kept there; the daily reset empties it).

## GM level
The client has one GM level byte. The server sends it from the account's permissions (`AdminLevel.Of`), in the Admin packet at field entry and again when `perm` changes the permissions:

| Account permissions | Level |
|---|---|
| Admin | 255 |
| GameMaster (all of its flags; finer flags on top do not matter) | 50 |
| anything else, also single flags such as Warp or SpawnItem | 1 (the client's own value for a player) |

The level only switches client features on (debug keys, filter skip, debug buttons). The client can raise it by itself, so every GM action is still checked on the server.

The GM grade byte in the party, guild and buddy views comes from the player info the World server keeps. A `perm` change is sent to World as a player update and goes on to the channels with the other profile fields, so those views follow it the next time they are sent. The field view and the Admin packet follow at once.

GM chat commands the client's own GM windows and hotkeys send (each needs the permission in brackets):

| Command | What the server does |
|---|---|
| `/MoveField <id> [flag]` (Warp) | move to the field |
| `/AddField <id>` (Warp) | a plain move to the field, the same as `/MoveField` |
| `/ClearInven` (GameMaster) | empties every inventory tab; worn items and the item of a summoned pet stay |
| `/ToggleInvisibleFromNpc` (GameMaster) | monsters do not pick the player as a target |
| `/ToggleDeathPower` (GameMaster) | each hit kills the monster it lands on; friendly NPCs and pets take normal damage |

The two toggles last for the session (they stay on across field changes and go off at a channel change, a relog, or when the account stops being a GM).

## GM-only packets
Some packets and packet modes are sent by the client only from a GM command, a debug hotkey or a developer dialog (the client tests its GM level or its debug mode before it writes them). A handler for one of those starts with `GmCheck.Allow(session, OpCode, mode)` (`Maple2.Server.Game/Util/GmCheck.cs`): the account needs the GameMaster or Admin permission, as set with the `perm` command. Any other sender is dropped with one warning (account id, opcode, mode) and gets no reply. A new handler or mode of that kind must start the same way.

The client's GM create windows are handled, each behind that check (a plain account changes nothing):

| Packet | Window | What the server does |
|---|---|---|
| 0x15 RequestItemCreate | item create | Needs SpawnItem as well. Creates the item (id, amount, rank) into the inventory by the normal add path. A rank outside 1-6 or an amount below 1 is refused. A stackable item gives one stack at most; other items give one per free slot; a currency id (meso, meret, experience orb and the like) gives 100,000,000 at most per request. A full bag answers with the inventory-full notice. An unknown id is refused. The period, level, enchant and option fields are read and not applied. |
| 0x24 RequestNpcCreate | NPC create | Needs SpawnNpc as well. Spawns the NPC at the position and rotation the window sends (1 to 50 per request, within 3000 units of the sender). One field instance holds at most 200 living GM-spawned NPCs, counted together with the `npc` command, which follows the same two limits. The NPC belongs to that field instance and goes with it. The pet button (pet flag set) is read and not handled. |
| 0x5C RequestAdditionalEffect | effect control | Mode 0 puts the effect (id, level) on the sender; the packet names no target. Mode 1 (reset) takes off the buffs this window created in this session that are still on. A buff the sender already had, or got again later from a skill or an item, stays. |
| 0x50 SetDebugMode | debug mode: minimap click (mode 2), NPC control (mode 4), debug guide commands (mode 7) | Mode 2 (a click on a minimap entity while the debug mode is on) moves the sender to the entity's position when the field accepts it. Mode 4 names an NPC by object id: picking the NPC is answered with DebugMode 0x0087 kind 6 (its skill list) and kind 5 (the window's text: movement state, AI file, battle target, physical and magic attack, defense, critical rate, health and its total; which texts retail put there is not known, these are the server's own choice; no AI trace is kept, so tracking is off; the extra list carries the NPC's AI values by key, at most 32; the AI file text is marked while the AI is switched off), and kind 5 is sent again after a health button, an AI on or off button, the AI file button and the extra button. The health buttons set its health (1 to 100 percent, or a value; never below 1 or above the total, so the window does not kill), the additional effect buttons put an effect (id, level) on it or take every buff of that id off. The skill button makes the NPC cast the first skill of the list once, facing the sender (the loop count and the rest of the list are not played); stop skill cancels the cast. That cast is a normal NPC cast: it hits players in range exactly like the NPC's own skill, so it is a GM tool to use with care. AI off (command 5) stops the NPC from choosing what to do next until AI on (command 4): its AI and idle steps are skipped, what it already does runs to its end, and its battle target is still kept up to date. The switch is logged with the account and lasts until the NPC leaves the field. The extra button (command 0xB) sends kind 5 again; the client has no reader of its own for that button, so what retail answered is not known. The AI file button (command 0xD) sends the path of an xml file picked under the client's Data/Xml/AI folder (uinpccontroldialog.cpp:576-591). The server takes the part of the path below that folder (or the bare file name) as the AI's name; a name it has no AI for, a text that is no xml name or one with a `..` part changes nothing and is logged. The NPC gets the named AI at its next update on the field thread: the AI it ran is dropped where it stood, its AI values and battle target stay. The change is logged with the account, lasts until the NPC leaves the field, and kind 5 is sent again with the new name. That the file replaces the NPC's AI is read from the button's name and its one argument; what else retail did with it is not known. The other buttons (battle setting, traces, assist, current additional) are read and logged, as are modes 0 and 9. Mode 7 (the debug guide window's multi execute button) carries 1 to 32 lines of command and argument, each text at most 256 characters; anything else is dropped. The lines are sent back as DebugMode 0x0087 kind 7 with the sender's name to the sender only; a client with the debug guide window open enters each line in its own chat, so every line comes back as that account's chat command and passes that command's permission check. No other client gets them, also not another GM in the same field: one GM cannot make another client run commands. The client hands every packet to every open window (networkservice.cpp:719, uiservice.cpp:1386), and its NPC control window reads kind 7 as an AI file name and an id and opens an AI debug window for it (uinpccontroldialog.cpp:233); the client sends nothing when that window closes, so once the sender has picked an NPC with the debug camera (mode 4, select) the lines are no longer sent back for the rest of that session (logged), until it logs in again or changes channel. Who retail sent kind 7 to is not known from the client; sender only is this server's own choice. |

The item and NPC windows need the same permission as the chat command that does the same thing (`item`: SpawnItem, `npc`: SpawnNpc), on top of the GM check. GameMaster alone holds neither flag, so a GameMaster account gets them with `perm` or is an Admin.

The client's debug mode (the GM buttons of the enchant, remake, exchange scroll and other dialogs) is toggled by key action 600001, the ` key in the client's default key file; the client turns it on only at GM level 50 or more. The key table the server sends holds that bind for a GM account only (added on ` or Scroll Lock when the saved table lacks it, taken out for a plain account). Every packet those buttons send is behind the GM check or has no handler.

A field with `enterAdminLevel` above 0 in its map file (8 test fields in the data: 80000000 and seven 99999xxx ids) is closed to plain accounts: every move into it is refused, and so is taxi travel to it (walk, car, rotors, meso call and the air taxi item), with the client's own message box, `s_field_limit_admin`. A plain character saved in such a field logs into its return field. A GM account passes. The value is read at ingest, so it needs a re-ingest.

The client reads no reply of its own for these three; it shows the normal item, NPC and buff packets.

## Two local changes a server operator must know

1. **All servers bind to loopback (127.0.0.1) by default.** To serve other machines, set `MS2_BIND_IP` to the address to listen on (`0.0.0.0` for all interfaces, as upstream); the server has no hardening for the open internet beyond upstream's.
2. **Test hooks.** Two environment variables turn on test hooks. Neither does anything unless it is set.
   - `TST_CMD_FILE`: once a second, the game server reads a file named after this prefix and the character id, and runs each line as a chat command **as the logged-in player**. Never set it on a server that others can reach.
   - `TST_PKT_DIR`: the server appends every packet that clients send, including chat, to a log file per character in this directory.
