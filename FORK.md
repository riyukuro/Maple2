# Maple2 for the KMS 2525 client

This fork is upstream [Maple2](https://github.com/MS2Community/Maple2) with fixes for the Korean MapleStory 2 client, build 2525. The branch is `kms2525`. Upstream's README.md is unchanged, which keeps merges from upstream simple. Setup and running are the same as upstream.

## How changes are made and checked

The changes in this fork are written by AI agents. Before a change is published it passes automatic checks (commit author, message and leak scans), an AI review of its diff, a Release build of the servers and the full test suite with the KR and NA locales. No person reviews the code, and most changes have not been tried in a live game; where a change was tried live, its commit says so. Commits whose subject starts with `UNREVIEWED:` went through the same checks: the prefix was only a working marker, and newer commits leave it out.

## How packet layouts are checked

Packet layouts are checked against the client source, not against another server. For each packet type and sub-type, a checker compares two things:

- Client to server: does the server read exactly the bytes the client's writer sends?
- Server to client: does the server write exactly the bytes the client's reader expects?

Each row gets one verdict:

- **pass:** the bytes match exactly.
- **warning:** the server writes more bytes than the client reads (trailing bytes).
- **fail:** the server reads past the end of what the client sends, the client would misread what the server sends, or the server does not handle a sub-type the client sends.
- **not checkable:** the client's reader or writer could not be followed automatically, or the server's code needs game state before it reads.

Every fix in this fork names the client function it follows (a file and line under the client source). The commit message quotes the checker's line before and after.

Results today:

| direction | rows | pass | warning | fail | not checkable |
|---|---|---|---|---|---|
| client to server | 680 | 239 | 5 | 67 | 369 |
| server to client | 1,193 | 592 | 4 | 0 | 597 |

The 67 client-to-server fails are all sub-types the server does not handle (listed below).

Server-to-client rows whose layout depends on client state are checked once per branch the client can take; a row passes when one branch reads the packet exactly. Of the server-to-client passes, 10 are weak (only a branch that ignores the packet, or a guessed condition, fits).

The four server-to-client warnings are kept on purpose; in each the client reads a prefix and ignores the rest:
- Trade sub-type 13 carries a trailing byte that the official server sends too.
- The skill state packet (sub-type 6) carries an extra int that shifts fields the client reads and then discards.
- The achievement favorite packet has no reader in the client (it handles sub-types 0 to 2 only).
- The skill macro load (sub-type 0) is read by a client handler that acts on sub-type 2 only.

## Fixes so far, by system

- **Opcodes:** client-to-server opcodes 0xAB to 0xBC are renumbered to the client's list.
- **Emote:** the list entry is 26 bytes; the favorite request (sub-type 4) is read as the client writes it.
- **Trigger:** the sub-type numbers are the client's (skip cutscene, UI, load script, save script, discard script).
- **Trigger dungeon variables:** a variable never set reads 0; no client code or table gives a start value.
- **Trigger score board:** score_board_score compares only in a field whose script called score_board_set_score; elsewhere it is the old test (the threshold compared with 0, so GreaterEqual passes). No kill, pickup or packet score reaches the board (the client only shows it), so 02020063/02020065 battle_1 (800 points) and 99999840/99999841 would otherwise never end. score_board_create now opens the client's board (0xE1, as the client reads it): type "ShadowGauge" as the boss gauge with the script's most points (02020063/02020065 battle_1), "ScoreBoardTopCenter" as the top-center score dialog (80000014/80000015 bonus); score_board_set_score sends the points to the open board (command 1) and score_board_remove closes it. The type "" (02020063/02020065 battle_2/3, 99999840/99999841) names no kind the client shows, so it still only logs. A player who enters while a board is open (from score_board_create or shadow_expedition_open_boss_gauge) gets it at its current points.
- **Trigger dungeon room timer:** a dungeon room whose row has a timerType (clock or gauge) and a durationTick gets that room timer when its first player enters; players who enter later get the running timer and its lap marks. With isExpireTimeOut the room closes when the time runs out, as bonus maps do. Without it, the time running out only makes dungeon_timeout pass. The actions follow the shipped scripts' own comments on them. dungeon_set_end_time ends the time function, so dungeon_timeout no longer passes; the room still closes at its time with isExpireTimeOut, which the scripts note must be blank for set_end_time to work. dungeon_close_timer closes the timer window (client command 5). dungeon_stop_timer stops the time and closes the window (4). dungeon_reset_time runs the timer again for the given seconds (2). dungeon_set_lap_time and dungeon_move_lap_time_to_now set a gauge mark, in milliseconds from the start, and send all marks (3). Without a room timer they do nothing and dungeon_timeout stays false. Choice: the server starts the timer at the first player's entry; the client does not show when the official server started it.
- **Dungeon missions:** a dungeon room's missions (its partyMissions, then its userMissions, the client's order) are now sent when a player enters a room field. The server first sends RoomStageDungeon mode 0, which is where the client makes its mission list and registers the DungeonMission handler. Missions score by the client's DungeonMissionData::GetScore. maxScore is split into applyCount steps; a row without applyCount has one step. A penalty mission starts full and loses a step's score per count. DamageToNpc counts a player's damage to the npc named in value2 (any npc without it): one step per value1 / applyCount. LastHitNpc counts a step when the player's hit kills an npc in value1. dungeon_mission_complete fills a mission as before. A user mission counts for the acting player. Choice: a party mission counts in every player's record of the room, because the client keeps one list per player. DeathCount counts a step at each death of the player in the room (all 46 rows are penalty, named for not dying). DamageBySkill counts a step at each hit (not a miss) on the player by a skill in value1; a row with value2 needs that skill level (one row). GainBuff counts a step when a buff in value1 is put on the player; a refresh of a buff it already has does not count (choice). PlayTime gets its full score when the room is cleared within value2 seconds of the dungeon start: every row's name gives a minute limit that is value2 / 60, value1 is not read, and the start is the room's entry (choice: the names do not say whether the time starts at the boss). The PlayTime packet's two times stay 0, the client shows nothing from them. dungeon_first_user_mission_score compares the sum of the first entrant's user mission scores. In the fame challenge rooms (one player each) that is the score the client's reward window shows.
- **Trigger dungeon level:** dungeon_level compares the room's groupType (2 raid, 3 chaos raid; the scripts' states are named so), not its dungeonLevel, which is a character level. Outside a raid or chaos raid room it keeps the old answer (3), so a script that tests only 2 and 3 still goes on.
- **Trigger dungeon max user count:** dungeon_max_user_count compares the client's DungeonRoom::GetMaxUserCount for the party size the room was made with (with isChangeMaxUser the size held between 2 and maxUserCount, else maxUserCount). The scripts test 1 to 4 only, so outside a dungeon room and in a 6 or 10 user room it keeps the old answer (1); dungeon_common/checkusercount has no other way on in a room.
- **Colosseum continue-play:** after the intro the Colosseum scripts run talk_npc on Nagi's spawn point; the server now starts that npc's talk with each player, as a click does (the client opens the talk window for a Respond it did not ask for, `UITalkManager::OnTalkPacket`). The choice's script function sets the DungeonPlayType user value (1 new game, 2 continue). The npc's script conditions `receivedRewardDungeonID` (a reward of the room was taken in its period, so the continue is offered) and `completeRewardDungeonID` (all were, so continue starts a new game) are read from the server pack's npcScriptCondition rows, which the parser does not read; their meaning is the server's reading of the names and the script flow (the client has no such table). Taken is the client's `DungeonRecord::GetBonusRewardCount` (the record's count while its cooldown period runs) against the room's rewardCount (`DungeonRecordCli::HasCountLeft`). set_user_value_from_dungeon_reward_count sets its key to that count of the room's one player, which for the Colosseum is its rounds cleared, so ClearRound starts the next round. A run that loses a round after the first ends with dungeon_clear uiType None; the server now clears the room there without the clear banner, so its rewards and the rounds it cleared are saved (before, only a run of all 13 rounds saved its rounds). A room takes one result: a later dungeon_clear or dungeon_fail changes nothing (no second result packet, clear count or dungeon_clear condition; logged at debug). The Colosseum is left out of that, because its script goes back to its start after each end and the next run in the same room ends with its own clear or fail. The conditions need a re-ingest; until then their rows check nothing, so continue is offered and always starts a new game.
- **Dungeon room cooldown from cooldownValue:** the client takes a room's cooldown type from its `cooldownValue` alone (`DungeonRoom::GetCooldownType`: 0 is the next day, any other value a day of the week) and ends the period at the next midnight of that day, numbered with Sunday 1, a week later when that day is today (`CalcCooldownEndTime`, `GetWeekdayStart`); the KR room table has no `cooldownType`. The ingest now sets the type the same way and keeps the value as the client numbers it, and a clear's reward period ends where the client's does. Before, the KR rooms had no type, their period ended at once and their reward count never held, so Nagi never offered the Colosseum continue after a run that cleared a round. Needs a re-ingest. A record whose period end was written by the older rule (a weekday counted from Sunday 0, at the clear's time of day) kept that end, which a clear only replaced once it had passed; now, at login and at a clear, a record still in its period whose end is not the rule's end gets the rule's end of its earliest possible clear (a period before the old end), its counts kept, so it ends with the week of that clear.
- **Dungeon fail result:** when a room changes to Fail, each of its players gets the reward packet with the fail flag and the room's seconds. The client's closing photo window opens the reward window when it closes (`UIDungeonClosingPhotoDialog`), and that window shows the fail title and the time from this packet (`UIDungeonRewardDialog::OnRewardPacket`); without it the window kept its placeholder text ("time", 0/0).
- **Dungeon season reward mail:** at the end of each season week the player is mailed the season's reward. The season total is the sum of the week's `CurrentRecord`s above 0 over the player's season rank rooms, as the client's `DungeonRecordManagerCli::GetTotalScore` sums them (dungeonrecordcli.cpp:580; the client has no caller of it and no cap); the server caps it at the season's `maxSeasonScore` (chosen from the name). The reward is the season's first reward whose `requireScore` is at most the total (`DungeonSeason::GetReward`, rewards highest first), an item with the row's `grade` and `count` (`DungeonSeasonItemGift` is an ItemEntity row; now ingested, so this needs a re-ingest), in a system mail with the season's `systemMailID`. The mail goes at the next login or weekly reset after the week's expiry (a week that ends while the player is offline is mailed at the next login); the week's scores are then set to 0, which also marks the week as mailed, so no migration is needed. A total below every `requireScore` mails nothing. Not tried live.
- **Dungeon extra reward event:** the `DungeonExtraReward` game event is now ingested (needs a re-ingest) from its value1 rows as the client's `DungeonExtraRewardCountCtx::Load` reads them: `dungeonID`, `count`, `cooldownType` (`dayOfWeeks` or `nextDay` by name, any case, else none) and `cooldownValue`; rows with no room or no count are skipped and a later row of a room replaces the earlier one. The event packet writes the id, then per room the key, room id, event id and count, as `GameEventDungeonExtraReward` reads them. A room's record keeps its own event count and expiry (`ExtraClears`, the new `ExtraCooldownTime` of `AddDungeonExtraCooldown`); the record's long after the extra count is that expiry (`m_extraCount`), where the server used to write the first-clear time. The enter check passes while the event count is not used up before the daily and weekly checks, as `DungeonRecordCli::HasCountLeft` tests it first. Chosen here (the client does not settle it): a clear takes an event count only when the weekly count and bought counts are used up; a none-type count lasts until the event ends; with several events naming a room the lowest event id wins (the client keeps the first it gets). Not tried live.
- **Item merge:**
  - Request and response sub-types are renumbered to the client's.
  - The option preview (Select) is written in the client's layout.
  - The merge table row is found as in the client: by the item's equip subtype for a material of subtype 1, else part 0, with the level limits and the row's `partLimit` list. A slot without `part` is part 0, as the client reads it (the parser gives 1; the ingest stores it under 0, so it needs a re-ingest). The materials offered are every inventory item the table answers for, asked by its table id, not the table's keys looked up as item ids. The list is read at ingest from the client's `table/itemmergeoptionbase.xml` (the played client's pack has the lists; the data folder's has none), so it needs a re-ingest; rows without it are not judged by it.
  - The merge table id is the material's `param1`, as in the client, when the ingest has the played client's pack (`MS2_PLAYED_CLIENT_XML`): the ingest reads it from that pack's `itemdata/*.xml`, and a material with a table id is asked by it first. Without that pack the table is asked by the material's item id. The hand copies of table 37000055 for 37000056..63 are made in both cases, only for an id with no rows of its own, so they serve only a material that got no `param1`. The data parser's item `Property` class has no `param1` field; with one, the data folder's own item xml could give it (the present data folder's item xml has no `param1` at all).
  - Known limit: the server's item rows come from the data folder's item xml, which is of another version than the played client's. There the merge materials have subtype 21 and 22 (the client's 1 and 2) and equips have subtype 0 or 16 (the client's is the id's kind, 12 to 83). So the equip subtype is taken from the item id (`id / 100000 - 100` for 112xxxxx to 183xxxxx, which holds for every equip in the played client's item data), and a material that is not of subtype 1 is still asked by part when its table has no part 0 row.

  - RideSync reads one trailing int per record.
  - The ride start request carries a byte after the object id, and the response echoes it.
  - Boarding another player's mount (ride join) follows the client's rule: the joiner and the owner are alive and a seat is free; the owner riding alone takes no one. The client's friend, party or same-guild check applies only with the RideShareAuthority feature, which is off in KR and NA (feature.xml level 99), so anyone may board and the server checks none of these either.

- **Party dungeon match (32, 33, 34):** a matchmaker in the World server. The rules are the user's choice (11-11), not read from the client:
  1. A match fills up to the room's maximum user count, dungeonroom.xml maxUserCount (the dungeon or raid cap), also for an isChangeMaxUser room. The client's DungeonRoom::GetMaxUserCount is not used for the match: for such a room it is the party size held between 2 and maxUserCount, the size of a room already made, so a search would count as full at 2.
  2. The party leader can stop the search early and go with the members found so far, at least the room's minimum. The client has no start-now control (no button, sub-type or confirm reply for it), so the closest client path is used: Party 34 (cancel) by the leader. When the search found someone and the party has at least the minimum of one of its rooms, the party enters that room; otherwise the search stops and the party stays as it is.
  3. A searcher joins an existing searching party for that room, the largest one with room for them, before a new party is started.
  4. The smaller goes into the larger, and on equal size the later into the earlier, whenever a group starts, as long as the merged size is at most a shared room's maxUserCount and the larger party's capacity. A party that starts a search merges into the largest searching party of the same kind, at least its size, that shares a room with it (the earliest on a tie); else it starts its own group, and that group then takes in the waiting smaller groups of its kind that share a room with it, the largest first, then the earliest, while they fit (their parties move into it as in a merge). The joining party's members move into the larger party (they leave theirs, which goes without a disband message) and the found count rises by their number. A merge or pull that fills the cap makes the room. A matched party cannot search again (error 43) and is not disbanded on a leave or kick while another member is online until its room is set; a party gone before then has its room destroyed. When a member move fails, the groups are put back as they were and no room is made; a party with a dungeon room set does not search (error 43) and is not merged.
  - From the client: Party 32 with no room ids searches the client's DungeonRoomTable::GetMatchRooms rooms (group types 1 and 2 by gear score, level limit and id, from the lowest member's level and gear score, at most DungeonMatchRecommendPickCount); with ids, only the picked rooms of the match kind whose level limit the lowest member meets. Party 33 searches its one room. The match kind is the client's map of the room's group type (normal and raid 1, worldBossDungeon 2, event 3, lapenta 4). The register reply (0x1e) and Party Load write the searching bits the client tests (bit kind; Load wrote a bool before); a stop writes 0. A match sends every member the match-found box (0x1f, which has only an OK button) and makes the room as a party dungeon, so the members enter it as from the party dungeon window.
  - Chosen here (neither the client nor the user settles it): no confirm wait and no decline, as the box has OK only; a member who does not press OK can still enter through the party dungeon. When several rooms are full, the lowest room id. Between groups of the same size, the one that started first. A joiner narrows the group to the rooms both search. Party 34 from a member who is not the leader gets error 40 (s_dungeonMatch_error_isNotChief); a Party 34 of another kind than the party's search, or with no search, changes nothing. A solo searcher who starts their own group gets a party of one (loaded before the register reply); a joiner or a merging party loads the party it moved into. Every member of the party counts for the group, its space, its full check and the leader's early start, online or not, so a party never passes the room's maxUserCount when someone comes back: a member who logs out keeps a slot, and the leader can kick them or start early. A leader who logs out (or is found offline before a search) hands the party over to an online member and the search goes on with the new leader; it stops only when no member is online. An invite, a leave or a kick resizes a searching group (it is matched when it becomes full, and stops when no room holds it); a group still searching then joins or pulls the others as a new search does. A searching party is not disbanded on a leave or kick while another member is online, so a party of two keeps its search for the member left; a disband ends the search with the stop (0x1e) first. When the search ends (stopped, cancelled, or its room cannot be made) a party of one is disbanded, with the disband message. When the room cannot be made the stop has already been sent. A search of a kind other than 1 with no picked room has no rooms and gets no reply. A party too large for every picked room gets no reply. The reward flag of Party 32 is not used; the inside-dungeon error (42), the client's enter count limit and the rooms' hidden flag and sortOrder (not ingested) are not checked. The register announce bool of 0x1e stays true. The party and queue state are under one lock in the World server; the channel calls a step makes (broadcasts, the room) are collected and made after the lock is released, and the room calls run on a task of their own with a deadline of 10 s (no answer = the room is not made). A leader change, the ready check, the kick vote and the recall are steps too, so their sends keep step order. A channel skips a member remove or disband for a party its player is no longer in. A party that moves away or is disbanded has its Party Finder listing removed. A join (an invite accepted, a Party Finder join) is refused with error 19 (the party is full; the client has no error of its own for it) while the party is matched and its room is being made, and while a dungeon room is set and the party holds that room's maxUserCount (also a room the leader made). A room the leader makes for the party is refused with error 43 while the party searches or is matched (Game tests the search before making it; when World refuses it, the room made is destroyed).

- **Dungeon recruiting (RoomDungeon 15 and 16, Party 39 and 43):** the party leader, or a player with no party, asks for helpers (15) or members (16) for a dungeon room. The World server sends the recruiting notice DungeonHelp 0x0109 (mode 0 for 15, mode 1 for 16; the layouts of UIMessengerBrowser) and keeps the recruit open for its chat link. The link's confirm box sends Party 39 (as a helper) or 43 (as a member) with the party id and the room id. From the client: the request carries only the room id; the client shows the buttons only for a room with a helperRequireClearCount, and drops a notice from a character it blocks, so the server does not filter blocks; the inside-the-cooldown answer is Party 40 with the milliseconds left. The user's rules (11-11): the notice goes to every online player whose level meets the room's level limit, outside a party that is full or in the matchmaker, and to the recruiting party's own members (the client starts its 10 s deadline only for its own party's notice). Party 39 and 43 both join as an ordinary member through the normal party join, held to the room's level, gear score (when the room has one) and maxUserCount; the joiner must have no party, the recruit must still be open for that party and room, and the party must not be searching or matched. A recruit closes when the party is full (its capacity or the room's maxUserCount), when its dungeon room is unset or set to another room, when it starts a match search, and 60 s after its notice; a closed or unknown recruit refuses 39 and 43. 15 and 16 get no reply when the notice goes out, and one party sends one notice per 10 s; inside that time only the requester gets Party 40 and nothing is sent to the party.
  - Chosen here (neither the client nor the user settles it): mode 0's last byte is the party's member count, all members online or not, as the matchmaker counts them. Mode 1's needMember is the room's maxUserCount minus all members (never below 0) and its needHelper is 0. Whether a joiner came as a helper or a member is not kept on the member. A recruit stays open 60 s. A player with no party who recruits gets a party of one, loaded before the notice; that party stays after the recruit closes, until the player leaves it. The 10 s wait is kept per party and per requesting character, and the larger time left is answered, so leaving or disbanding the party and recruiting again does not reset it; a requester's wait is dropped once it is over. The requester is held to the room's level and gear score like a joiner (errors 17 and 18, before any party is made). A party whose dungeon room is set to another room gets error 43 (s_party_err_dungeon_match_another), not RoomDungeon 27, whose text is about the search being switched off. A room with no helperRequireClearCount, or with the helper search off (disabledFindHelper), keeps the client's text for the search being switched off (RoomDungeon error 27). A request from a member who is not the leader gets error 4 (s_party_err_not_chief); from a party that is searching or matched, error 43; from a party that already holds the room's maxUserCount, error 19. A join refused for the joiner's own party gets error 5 (s_party_err_already); to a closed or unknown recruit, error 31 (s_party_err_not_found); to a party searching or matched, error 43; under the level or gear score, errors 17 and 18; over the room's maxUserCount, error 19. A new notice of the same party replaces its open recruit (and its kind and room). The client's own clear count gate (under 10 clears) is not checked by the server.

## Database migrations
The servers do not migrate the game database when they start. After an update that adds a migration (`Maple2.Server.World/Migrations`), run `dotnet ef database update` in `Maple2.Server.World` (the ingest runs the same command) before the servers start. Without the `home-block` table of `AddHomeBlockTable` every login fails, because the home block list is read at login. Without the `nurturing-daily` table of `AddNurturingDaily` feeding a housing pet or playing with one fails (the daily record of feedings and plays is kept there; the daily reset empties it). Without the `dark-stream-record` table of `AddDarkStreamRecord` the end of a Dark Stream run fails to read and keep the best score, and the web ranking's Dark Stream boards fail. Without the `boss-clear` and `boss-clear-member` tables of `AddBossClear` the clear of a raid, chaos raid, reverse raid, lapenta, turka or fame challenge room with a BossRanking fails to keep its row, and the web ranking's boss and fame challenge boards fail. Without the `Damage` column of `AddBossClearDamage` every boss clear fails to keep its row, and the web ranking's boss, fame challenge and world boss boards fail. Without the `colosseum-record` table of `AddColosseumRecord` the end of a Colosseum run fails to keep the best run, and the web ranking's Colosseum board fails. Without the `ExtraCooldownTime` column of `AddDungeonExtraCooldown` every dungeon record read fails. Without the `home-commend` table of `AddHomeCommend` every login fails (the last commendation time is read at login), and so do loading a home and the web ranking's house board. Without the `maid` table of `AddMaid` removing any cube fails, and so does loading a home with a maid furnishing (after a re-ingest). Without the `FamePoints` column of `AddFamePoints` every character load fails (the column is read with the rest of `character-unlock`).

## GM level
The client has one GM level byte. The server sends it from the account's permissions (`AdminLevel.Of`), in the Admin packet at field entry and again when `perm` changes the permissions:

| Account permissions | Level |
|---|---|
| Admin | 255 |
| GameMaster (all of its flags; finer flags on top do not matter) | 50 |
| anything else, also single flags such as Warp or SpawnItem | 1 (the client's own value for a player) |

The level only switches client features on (debug keys, filter skip, debug buttons). The client can raise it by itself, so every GM action is still checked on the server.

The GM grade byte in the party, guild and buddy views comes from the player info the World server keeps. A `perm` change is sent to World as a player update and goes on to the channels with the other profile fields, so those views follow it the next time they are sent. The field view and the Admin packet follow at once.

GM chat commands the client's own GM windows and hotkeys send (each needs the permission in brackets):

| Command | What the server does |
|---|---|
| `/MoveField <id> [flag]` (Warp) | move to the field |
| `/AddField <id>` (Warp) | a plain move to the field, the same as `/MoveField` |
| `/ClearInven` (GameMaster) | empties every inventory tab; worn items and the item of a summoned pet stay |
| `/ToggleInvisibleFromNpc` (GameMaster) | monsters do not pick the player as a target |
| `/ToggleDeathPower` (GameMaster) | each hit kills the monster it lands on; friendly NPCs and pets take normal damage |

The two toggles last for the session (they stay on across field changes and go off at a channel change, a relog, or when the account stops being a GM).

## GM-only packets

The own rank is the asking account's home. Not settled by the client, chosen here: most commendations first, then the home that reached its count first, then the account id; the owner's character is its last played one, a home whose account has no character is left out; the best 200 rows, and with a search name the row of that character's home.
- Web ranking (irrq.aspx) requests of type 0: the ranking dialog sends a request whose key type is 0 when the board it shows has no tab. `UIGameRankingDialog::BuildRankingKey` and `BuildMyRankKey` return before `CGameRankingCli::BuildKey` without a tab, and the season boards (Dark Stream 3, Colosseum 0x10 and the others with a SeasonRankType) only get tabs from a season of the client's own Table/SeasonData_<type>.xml whose start and end hold the server time (`CSeasonDataTable::Refresh`, `GetUpcoming`). ## Two local changes a server operator must know

1. **All servers bind to loopback (127.0.0.1) by default.** To serve other machines, set `MS2_BIND_IP` to the address to listen on (`0.0.0.0` for all interfaces, as upstream); the server has no hardening for the open internet beyond upstream's.
2. **Test hooks.** Two environment variables turn on test hooks. Neither does anything unless it is set.
   - `TST_CMD_FILE`: once a second, the game server reads a file named after this prefix and the character id, and runs each line as a chat command **as the logged-in player**. Never set it on a server that others can reach.
   - `TST_PKT_DIR`: the server appends every packet that clients send, including chat, to a log file per character in this directory.

**LOCALE must be the played client's locale.** The server takes script branches and locale rows from LOCALE, the client from its own region; with a KR client and LOCALE=NA, for example, the client lets an outfit with no break row be dismantled (its KR script gives lucky bag coupons) while the server's NA branch previews and pays nothing. The ingest prints a warning when MS2_PLAYED_CLIENT_XML is set and its pack's region (its one table/<region>/ folder) is not LOCALE.
